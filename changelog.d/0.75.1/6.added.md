- **Layer streaming accepts DeepSeek-V3 (`model_type=deepseek_v3`) (#6).** The sharder stacks per-expert checkpoint keys into the fused experts transformers 5.19 builds, drops the MTP layer, and the runtime loads the router bias from the checkpoint and keeps it in fp32. A tiny synthetic model streams bit-exact against a resident one in fp32 on an RTX 3050 (and on CPU, except NF4, which needs a GPU), for forward, backward, NF4, the disk tier, LoRA on attention and `moe_lora` on the routed experts; NF4 leaves the routed experts at the base dtype. `trust_remote_code: true` is refused for DeepSeek-V3. A local folder whose `config.json` has `auto_map` (every DeepSeek-V3 download) no longer needs `--trust-remote-code` when its `model_type` has a built-in transformers class, because transformers ignores `auto_map` then. An unknown `model_type` still needs the flag. `soup export` for AWQ and GPTQ also still needs it when `tokenizer_config.json` names a Hub tokenizer. The architectures `kimi_k2`, `deepseek_v32`, `deepseek_v2` and `kimi_k25` stay refused. No real DeepSeek-V3 checkpoint has been streamed. The compatibility table and raw logs are in `benchmarks/gate-b2-deepseek-v3.md`.

- `target_modules: auto` on a DeepSeek-V3-shaped model (`deepseek_v3`, `kimi_k2`, `kimi_k25`) with `q_lora_rank: null` now adapts the single `q_proj` instead of the absent `q_a_proj` and `q_b_proj`. Before, the query projection got no adapter. Models with a `q_lora_rank` (V3, R1, Kimi K2) resolve as before (#6).

- `moe_lora: true` on DeepSeek-V3 now adapts the MLA attention projections (`q_a_proj`, `q_b_proj`, `kv_a_proj_with_mqa`, `kv_b_proj`, `o_proj`) as well as the routed experts. It named `q_proj`, `k_proj`, `v_proj` and `o_proj` for every MoE model, so on DeepSeek-V3 only `o_proj` got an adapter. `deepseek_v4`, `glm_moe_dsa`, `kimi_k2` and `kimi_k25` now get their own attention names the same way. Architectures whose attention is `q_proj`, `k_proj`, `v_proj` and `o_proj`, and those without a table entry, keep their targets (#6).
