# A2 ticket 03: L2L против накопления градиентов при dropout 0.05, SmolLM2-135M, RTX 3060, 2026-10-22

> **Устарело для текущего кода (2026-10-23).** Этот отчёт измерен на варианте А: состояние слоя
> задавала функция `layer_seed(seed, step, mb, layer)`, эталоном было накопление с теми же хуками.
> По ревью PR #31 вариант А заменён на replay нативной последовательности (`utils/l2l_rng.py`),
> эталон теперь обычное накопление без хуков. Ниже записано, что проверено на варианте А.
> На варианте Б CUDA-прогона ещё не было: `benchmarks/harness/l2l_smollm2_check.py --dropout 0.05`
> нужно запустить заново (флаг `--rng-step` убран).

**Вердикт: PASS.** При dropout 0.05, одном seed и шаге потери и все 240 LoRA-градиентов L2L равны
накоплению с теми же хуками состояния (`torch.equal`) для k=1, 2, 4. Второй запуск в отдельном
процессе даёт те же значения (одинаковый sha256 потерь и градиентов). Оба контрольных прогона с
неправильным порядком случайности показывают отличие. При dropout 0 результаты A1 воспроизводятся.

Проверялся поставляемый `soup_cli.utils.l2l_step.L2LStep` с `ActivationStore` в закреплённой
хостовой памяти (`pin=True`) на коммите 9a437933 (драйвер) и b396f16e (скрипт fit, на сервер
загружен отдельно; хеши файлов в `source-sha256.txt` совпадают с локальными).

## Результаты (реальная модель, синтетический вход)

Реальные веса SmolLM2-135M, случайные токены на входе. Качество модели не измерялось.
Синтетические результаты на крошечной модели (тикет 02, `tests/test_l2l_rng_cuda.py`) и A0 (dense-70B)
в этот отчёт не входят.

| Прогон | dropout | k=1 | k=2 | k=4 |
| --- | --- | --- | --- | --- |
| d0-01 | 0 | потери и градиенты равны | равны | равны |
| d005-01 | 0.05 | равны | равны | равны |
| d005-02 (повтор) | 0.05 | равны, sha256 как в d005-01 | равны, sha256 как в d005-01 | равны, sha256 как в d005-01 |

Во всех записях 240 тензоров (30 слоёв x 4 проекции x A/B), максимальная разница 0, нулевых
градиентов нет, A-против-A (два прогона эталона) побитово равны.

**Dropout 0 воспроизводит A1.** Потери `losses_l2l` и счётчики загрузок из `d0-01/records.json` совпадают
с `none-01/records.json` из A1 для k=1, 2, 4: загрузки слоёв L2L 58, 58, 58, накопления 58, 115, 229.
В прогоне 1 драйвер был 595.104.02, в A1 и в прогоне 2 595.91.07. Режим драйвера при dropout 0 не менялся (обычное `ga_step`, без хуков).

**Dropout действует.** Sha256 при dropout 0.05 отличается от sha256 при dropout 0 для каждого k.

**Контрольный прогон с неправильным порядком.** При dropout 0.05 для каждого k драйвер сравнивает
результат L2L ещё с двумя прогонами, и оба расходятся с ним (`control_stock_stream_equal` и
`control_shared_stream_equal` равны `false` для k=1, 2, 4 в обоих прогонах):

1. Накопление на одном потоке случайных чисел (`torch.manual_seed(seed)`, обычный `ga_step`, как в стандартном Trainer).
2. L2L, у которого вызовы слоёв делят один поток (функция состояния слоя заменена пустым контекстом, как в A1).

Размер расхождения в записи не сохраняется, только флаг равенства, поэтому сам по себе `false` не
отличает расхождение порядка от любой другой недетерминированности. Против этого есть косвенные
доводы: эталон дважды совпал сам с собой (A-против-A) и с L2L, а два запуска дали одинаковый sha256.
Контроль 2 тоже ставит `torch.manual_seed(seed)` один раз и расходится с L2L по построению: он
показывает, что общий поток не воспроизводит маски, а не изолирует отдельную причину.

**Загрузки слоёв.** При dropout 0.05 L2L грузит 58 слоёв при k=1, 2, 4, накопление 58, 115, 229.
Счётчики A1 не сломаны, число загрузок не растёт в k раз.
