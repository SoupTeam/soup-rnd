# A0: результаты и контроль воспроизводимости, 2026-10-19

**G1–G4 PASS; полный batch-control на этом стенде остаётся неподтверждённым.**

Gates относятся к исходной сессии 01. Весь дополнительный batch-блок precision 03
оценён отдельно: пары и отдельные строки разных попыток не объединялись.
Изменение числа шагов зафиксировано до запуска и явно приведено ниже.

Исходные трёхшаговые попытки сохраняют свои INVALID / incomplete. Увеличенный
замер не является утверждением, что исходный трёхшаговый протокол воспроизвёлся.

## Что известно о разбросе I/O

В control 02 при одинаковых ~69.94 GB чтения на шаг batch 1 время менялось
с 23.84–23.87 s до 36.88–41.56 s. Средняя наблюдаемая скорость nvme0n1
снижалась с ~2.89 GB/s до ~1.65–1.81 GB/s при занятости ~96–98%.
Это свидетельствует о вариабельности обслуживания пути чтения; конкретная
причина на уровне SSD, хоста или планировщика не установлена.

В самых медленных точках batch 1/3 заметных записей не наблюдалось.
Источник отдельных записей других точек не атрибутирован. Конкуренция с
другими арендаторами остаётся гипотезой. Доступный cgroup CPU throttle counter
равен нулю, swap.current равен нулю; это не исключает ограничений вне видимости
контейнера. Температуры precision 03 не доказывают перегрев; critical threshold
не равен обязательно порогу троттлинга.

Длинные пары batch 1/3 прошли V4, короткие batch 2/4 — нет. Это основание
проверить единый заранее зафиксированный длинный контроль, а не доказательство
устранения причины. Full 04 запущен 2026-10-19 в 21:11 UTC+5 на том же инстансе; выполняется.
Все batch 1–4: 2 warmup +24 measured steps, два раунда; допуск 5% без изменений.
Итоговый вердикт 04 появится после завершения полного блока.

[Данные диагностики и ограничения вывода](results/a0-vast-rtx3070/io-diagnosis.json).
После precision 03 GPU idle: 1 MiB, 0%, вычислительных процессов нет.
Аренда инстанса продолжается.

## Вывод для A0 / A1 / B1

На этом shared-хосте контроль не подтвердился даже в дополнительном профиле.
Невалидные строки не используются для закрытия A0. Перед новым измерением
следует проверить единый длинный профиль либо другой стенд, затем оценить полный блок.
G1–G4 исходной сессии остаются PASS; вывод о полном закрытии batch-контроля не делается.

R&D-документ называет его историей реализации, а не текущими требованиями.

`293ed494b374ecaebe7b4efc4e2bac8fcdffb3c8`: handoff и .claude не отслеживаются.

104 CPU-теста и Ruff изменённого harness прошли до замеров. Production src/ не менялся.

## Исходная сессия 01: сохранённый результат

**Измерения завершены. G1–G4 PASS; полный ordinary-batch контроль не закрыт из-за V4 на batch 1/2/3.**

L2L k16: **74.84 tok/s**, ускорение **3.457×** относительно L2L k1; peak allocated **4.095 GB**.
Обычный batch 4: **78.71 tok/s**, peak allocated **7.360 GB**. На этой конфигурации L2L
медленнее него на **4.91%**, но расходует на **44.36%** меньше выделенной GPU-памяти.
Максимальный batch для измеренной конфигурации — **4**: batch 5 дал CUDA allocator OOM
в двух отдельных процессах. Это граница текущих настроек allocator/runtime, не всех возможных настроек GPU.

### Решение по A1 и B1

- **A1:** механизм прошёл G1–G4, но включение L2L по умолчанию ради скорости dense-70B
  на этой карте не обосновано: валидный обычный batch 4 быстрее. Прототип имеет смысл
  отдельно оценивать ради экономии VRAM или задач, где обычный batch ограничен памятью.
- Полное подтверждение ordinary-batch 1/2/3 требует новой заранее зафиксированной попытки
  в quiet window. Невалидные строки этой попытки сохранены; переизмерений с выбором лучших строк нет.
- **B1:** отдельная проверка MoE остаётся следующим исследованием. Этот замер не доказывает
  качество обучения, сходимость или скорость гигантских MoE. A1/B1 и C4 здесь не реализовывались.

### G1–G4 и валидность

| Gate | Статус | Результат |
| --- | --- | --- |
| G1 | pass | F1: 256 tensors + losses equal (deterministic); F2: 640 tensors + losses equal (deterministic) |
| G2 | pass | T_A(16) 74.8 vs 0.8 x T_B(16) 60.0 tok/s |
| G3 | pass | T_A(16) 74.8 vs 1.3 x T_A(1) 28.1 tok/s |
| G4 | pass | peak A16 4.095 vs A1 3.968 + 0.5 GB |

G1 использует предусмотренный исходным правилом deterministic fallback: обычный GA
не был битово воспроизводим сам с собой на F1/F2. В fallback GA/GA и L2L/GA совпали
точно: F1 256 и F2 640 ненулевых gradient tensors, плюс per-microbatch losses.

V1: direct I/O подтверждён. V2: plain и L2L k1 имеют 158 загрузок и 69.937 GB на шаг.
V3: перед CUDA 4 MiB, peers нет; доступно 23.026 GB RAM для 10.737 GB pinned + 4 GB margin.
Проверены 44 arm records и 88 GPU snapshots: везде один собственный
GPU PID, нет видимых тяжёлых чужих читателей; V5 не обнаружил battery/unknown samples
или gap >30 s. Все token-row fingerprints совпадают с общей последовательностью.
V4 проверялся для каждой пары; не прошли только отдельные ordinary batch 1/2/3.

Linux-питание явно декларировано как server, физического AC-датчика нет.
Чужой I/O наблюдается только в пределах процессов, видимых контейнеру; отсутствие
конкурирующего I/O других контейнеров/хоста этим не доказано. Причина разброса batch 1/2/3 не установлена.
