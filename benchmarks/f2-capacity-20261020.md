## Hardware and allocation

The selected rental is an RTX 5060 Ti 8 GB, with one physical Samsung NVMe.
The provider assigns `memory.low = 32,028,753,920` bytes as the baseline RAM
allocation. `memory.max = 56,060,018,688` bytes permits temporary bursting;
neither that burst ceiling nor the approximately 101 GB physical host is the
32 GB baseline. `memory.low` is protection, **not a kernel hard limit**.
Record all three values, initial baseline-free bytes, physical GPU UUID/VRAM,
driver and package versions. Require baseline >=32e9 and <=36e9 bytes, initial
baseline-free RAM >=32e9, and a genuine single NVMe. No RAM-filling process,
changed cgroup, paging, power or clock setting is permitted.

The shipped RAM probes previously saw the entire host through psutil. A
tested production repair uses actual visible container allocations and
reclaimable clean file-LRU pages. A positive reservation supplies the safe
baseline budget; a smaller hard/ancestor limit still applies. The existing
0.7 available-memory and 0.55 total-memory safety fractions are unchanged.
Automatic overflow must occur in ordinary Soup code with `stream_source:auto`;
the harness never patches memory readings or forces a disk tier.
