# D1: штатная BF16-арифметика и короткие проверки пользы для Soup

Актуальный итог: [большой decoder, VRAM и вердикт для сдачи](d1-final-result-20261016.md).
Ниже сохранён предыдущий этап; его маленькие пилоты не являются итоговым product claim.

**Штатная корректность исправлена; получен перспективный пилот ускорения.**
Production Soup пока не переключён: результаты ниже достаточны для research review,
но не закрывают полную приёмку D1/F1 и не доказывают ускорение рабочих моделей.
Этот отчёт заменяет текущий вывод [предыдущего WMMA-отчёта](d1-wmma-result-20261016.md),
который сохранён вместе с неуспешными экспериментами.

## Что изменилось

На большом backward native cuBLAS запускает CUTLASS с grid.z=4. Полное FP32-накопление
отличалось от штатного результата. Проверены три конкретные гипотезы округления;
совпала последовательная схема: четыре суммы по 8192, после каждой BF16-округление
с добавлением предыдущего округлённого результата. Две альтернативы не совпали.
Это наблюдение для данного GPU/стека/формы, не универсальный контракт cuBLAS.

Новый явный исследовательский backend `wmma_native64`:

- декодирует NF4 внутри shared-memory плиток, без полной промежуточной BF16-матрицы;
- сохраняет все шесть тензоров через `save_for_backward` и проверяет владельца слота;
- повторяет найденное округление большого dX, сохраняя штатное значение
  `allow_bf16_reduced_precision_reduction=True` у native и кандидата;
- на большой форме переиспользует уже fused forward bitsandbytes;
- группирует работу нескольких warps и читает packed weights dX последовательно.

`wmma_native` — проверенный вариант плитки 32, `wmma_native64` — плитка 64.
Они выбираются только явным аргументом benchmark API. Production dispatch не менялся.
API ограничен проверенными (M,N,K): (128,64,64), (2048,64,64), (128,4096,4096),
(128,32768,12288). Проверенный стек: RTX 3090 sm86, Torch 2.11.0+cu126,
bitsandbytes 0.50.2, BF16, вложенные NF4 scales. Перенос на другой стек требует gate.

## Корректность

Для обеих плиток при штатном режиме:

- 192 MiB packed-буфер: forward и dX exact относительно native resident;
  checkpoint повторно вызван дважды после перезаписи весов и scales;
- в том же процессе plain-ctx контроль дал конечный, ожидаемо другой dX;
- настоящий streamed Llama decoder Soup, 4 слоя / 2 буфера, seq128 и seq2048:
  logits и все 16 наборов ненулевых LoRA-градиентов exact; resident не патчен;
- по три последовательных полных LoRA/SGD-обновления на проекции и на streamed
  decoder: выходы/потери, градиенты и обновлённые адаптеры exact;
- независимый CPU-аудит сохранённых CUDA-тензоров, хэшей и исходников прошёл.

Большая арифметическая гипотеза проверена на seed842, recycled-buffer gate — на
других весах seed99991. Повторные одинаковые fixtures не выдаются за новые seed.
Локально: **131 passed, 13 hardware skips**, Ruff и diff-check чистые.
Новые #842/#968 GPU pytest отдельно не запускались; новый CUDA harness проверил
checkpoint и resident parity, а локальные GPU tests остались явно пропущенными.

Выполненные версии: плитка32 — `4e762055` (полный SHA в evidence), плитка64 —
`538588b554ea836c63e4e038deb3f0c3fd2fb476`. После запусков изменены только
форматирование и ограничение API до фактически проверенных форм.

## Короткие полные шаги

Все строки — отдельные пилоты на одном GPU; прежние аренды и K-сетка сюда не подмешаны.
Три чередующихся блока: по 1000 шагов на проекции, по 200 на decoder.

| Путь | Плитка | Native, мс/шаг | Кандидат, мс/шаг | Отношение candidate/native |
|---|---:|---:|---:|---:|
| Одна проекция 4096×4096, M128, LoRA rank8, SGD | 32 | 2.418 | 2.533 | 1.048 |
| Та же проекция | 64 | 2.379 | 1.815 | 0.763 |
| Полный streamed decoder Soup, hidden64, 4 слоя, seq128, SGD | 32 | 50.222 | 45.713 | 0.910 |
| Тот же decoder | 64 | 52.850 | 47.775 | 0.904 |

В проекционном шаге peak allocated уменьшился с 119809024 до 95433728 байт:
**−23.25 MiB**. Peak reserved одинаковый: 146800640 байт. В маленьком decoder
allocated отличается лишь на **8192 байта**, reserved одинаковый: 90177536 байт.
Экономию проекции нельзя объявлять экономией всей модели.

Профиль проекции содержит 1695–1950 MHz, поэтому его 23.7% меньшего времени нельзя
выдавать за подтверждённое ускорение. В decoder SM оставалась 1695 MHz, memory
utilization записана (0% на этом маленьком fixture). Однако это один процесс,
три блока, без полного F1 ArmWatch и fresh-process ABBA. **Формальный perf verdict:
NO_VERDICT**, в том числе для наблюдаемых 9.6% на decoder. Same-session dense GEMM
измерен после peak capture проекции; сырые окна и телеметрия сохранены.

## Что это даёт Soup

Получен работающий способ убрать BF16-распаковку веса из dX, сохранив native
арифметику и корректность recycled buffers. Польза по памяти измерена на полном
LoRA-шаге; улучшение времени в пути Soup наблюдалось на небольшом decoder.
Это конкретный кандидат для следующей проверки на целевой модели, а не готовая
гарантия ускорения 8B/70B. Повторять прежний долгий тренинг ради этой гипотезы
не потребовалось. Новых pretrained quality-прогонов не было.

Для полной сдачи карточки остаются независимый review, покрытие целевых форм/типов
и валидное сравнение полного шага целевой модели по F1. До этого рекомендован
research review; автоматическое включение в Soup — NO GO. Новый бюджет не требуется
для проверки и обсуждения приложенного пакета; дополнительные GPU-прогоны не запущены.

частей `raw-native.tgz.part*`, SHA-256 полного архива и каждого файла.

dispatch. PTX реально выполненных staging-проверок лежит в `split2/tile-*.ptx`.
