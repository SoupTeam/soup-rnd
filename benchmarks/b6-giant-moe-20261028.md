# B6: real DeepSeek-V3 671B on one 8 GB GPU

The real checkpoint completed two backward/AdamW adapter updates on a physical
RTX 5060 8 GB. Reloaded adapter parameters match the trained digest and validation
logits are bitwise equal (maximum absolute error 0). The independent journal
checks pass. This is a two-step capacity/reload pilot; the 32 GB RAM target and
general model quality remain unvalidated.

The [October 29 review follow-up](b6-acceptance-20261029.md) records the CI fix,
approved paired-evaluation protocol, rejected RAM/VM probes and cumulative cost.
It contains no new real giant measurement and does not close the RAM acceptance item.

The branch builds on SoupTeam main 9d8b1d7b. Frozen experts refetch inside a
bounded lease for backward. CPU tests cover routing gradients, activation
contract, checkpoint recompute, failures and adapter save/reload. CUDA correctness receipts and the separate real-pilot results are retained below.

## Disk preparation

`utils/expert_cache_budget.py` reads only bounded safetensors JSON headers,
including FP8. Its narrow budget is for a new NF4 cache on one disk without
nested statistics. It includes conservative dense weights, expert NF4 payload,
metadata, an extra largest layer for temporary writes and a tied-head allowance.
The expert writer validates NF4 output shapes/dtypes/blocksize before writing.
Every atomic shard write separately checks actual payload and free bytes while
preserving an existing destination on refusal. This does not reserve space
against concurrent writers.

Real DeepSeek-V3 header-only plan, revision
`e815299b0bcbac849fa540c768ef21845365c9eb`:

- 163 source files, 688,586,727,753 source bytes.
- 91,991 header tensor entries; 45,312 routed-expert matrices.
- Conservative cache budget: 519,579,082,752 bytes, including reserve.
- This is the conservative header calculation; measured cache bytes are recorded below.

## Real pilot hardware and preparation

The completed pilot used one physical RTX 5060 (8151 MiB by nvidia-smi;
8,122,859,520 bytes visible through torch), driver 610.57.04, Python 3.12.3,
torch 2.8.0+cu128 and CUDA 12.8. The CPU is Ryzen 9 5950X. Host RAM is
134,948,118,528 bytes; the container memory limit is 129,549,467,648 bytes.
This is a larger-RAM host than the proposed 32 GB target. The allocated root
filesystem is 1,503,238,553,600 bytes (1400 GiB) on CT4000P3PSSD8 NVMe.

All 163 source files were downloaded at the pinned revision; their exact total
is 688,586,727,753 bytes. Download wall time was 552.10 seconds, including a short
pause to raise the allowance for network acknowledgements while retaining the
same overall spend/deadline guard. This is not a network bandwidth benchmark.

Two meta-construction attempts were interrupted before cache writes: deterministic
poison fill made temporary CPU `torch.empty` arrays touch giant amounts of memory
before Accelerate redirected the parameters to meta. The diagnostic stack points
to the experts constructor. The successful preparation disables poison fill only
inside structure construction and restores the previous setting afterward.
Dynamo is disabled for this pilot; no compiled-path speedup is claimed.

A first one-thread preparation was stopped with an incomplete cache. On one real
FP8 expert gate matrix, three decodes at each of 1/4/8 CPU threads were bit-exact.
Median times were 0.16236 / 0.05337 / 0.03988 seconds. The preparation was restarted
with 8 threads, rebuilding the incomplete cache; training restores one thread.
Those sample times do not establish an end-to-end speedup. Interrupted attempts
are retained separately and are not pooled into training timings.

## Protocol and command

This is a capacity and artifact-reload pilot of the real DeepSeek-V3 checkpoint,
not a synthetic parameter-count simulation. The indexed causal decoder has
671,026,419,200 parameters, 61 layers, 58 routed-expert layers and 256 experts per
routed layer. The entire 163-file upstream source was downloaded. The causal
model does not exercise the checkpoint's separate multi-token-prediction module.
The source FP8 matrices are converted to an NF4 cache without double quantization;
base weights stay frozen. BF16 is the compute dtype.

The adapter targets `q_a_proj`, `q_b_proj`, `kv_a_proj_with_mqa`, `kv_b_proj` and
`o_proj`: rank 2, alpha 4, dropout 0, bias none. It does not adapt routed experts.
AdamW uses lr 1e-4 and its torch defaults, with gradient norm clipping at 1.0.
There are exactly two optimizer steps, batch size 1, no accumulation, maximum
length 64, unpadded. Actual token counts are logged, including shorter examples.
Training and validation use one CPU thread; cache conversion uses eight.
Global torch seed is 20261028; the streamed model builder's adapter seed is 0.

The developer-authored data is [b6-pilot-data.json](../examples/b6-pilot-data.json):
two training strings and one heldout string, SHA-256
`0fc5d9740230def5280506044cabfe355b2f9228a38e256ade1973b4b16cd1f5`.
There is no task benchmark, reference-model quality comparison or convergence
claim. Heldout loss is recorded even if it gets worse.

Run from the repository root after downloading the pinned source revision and
installing the versions in the evidence's pip freeze:

```bash
export PYTHONPATH="$PWD:$PWD/src"
export CUDA_VISIBLE_DEVICES=0 PYTHONHASHSEED=0 USE_TF=0 TOKENIZERS_PARALLELISM=false
export OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 CUBLAS_WORKSPACE_CONFIG=:4096:8
export TORCHDYNAMO_DISABLE=1 HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1
python benchmarks/harness/b6_real_moe.py \
  --source /root/b6/source --cache /root/b6/cache \
  --output /root/b6/results/new-run --data examples/b6-pilot-data.json \
  --revision e815299b0bcbac849fa540c768ef21845365c9eb \
  --steps 2 --max-length 64 --shard-threads 8
```

Use a new output directory. Omit cache flags for the first conversion; use
`--reuse-cache` only for a complete, validated cache, or
`--restart-incomplete-cache` for a deliberately restarted incomplete conversion.
Reusing the cache does not measure conversion time. The cache source fingerprint,
layout, dtype, quantization and files are checked before reuse.

## Preparation measurements and failed reload trial

The completed conversion took 2568.94 seconds (42.82 minutes), producing
380,276,447,824 cache bytes. This is below the conservative header budget of
519,579,082,752 bytes. After preparation the filesystem had 426,840,158,208 free
bytes. Preparation's process peak RSS was 17,249,882,112 bytes. RSS excludes OS
page cache and is not evidence for a hard 32 GB RAM limit. Source reads were warm
from the earlier interrupted attempt; this is not a cold-cache I/O benchmark.
All 58 open routed-expert file descriptors were observed with `O_DIRECT` flags.

Trial `real-retry3` completed both optimizer steps and saved a 48,587,072-byte
adapter. Its heldout loss changed from 4.5601024628 to 4.5665259361. Reload then
failed before logits evaluation because CUDA rounded an expert arena above its
logical byte budget. That trial does not pass the reload acceptance gate. Its
journal and failure log are retained separately from the repeated trial.

The fix adds an explicit 32 MiB CUDA allocator reserve to both preflight and
runtime budgets while retaining an observed-allocation hard check. In two fresh
real-model structures, logical expert storage was 112,853,504 bytes and observed
CUDA allocation was 113,246,208 bytes, within the 146,407,936-byte budget. All
saved adapter parameters loaded exactly in both structures. These builds alone
are not a forward/reload-logits result. The repeated training trial also saves
reference logits before replacing the model, checks the final parameter digest
and requires bitwise-equal validation logits after reload.

Trial `real-retry4` starts from a fresh adapter and reuses the validated complete
cache. It is not continuation of the previous adapter or a new cache conversion.

or claiming a speedup. No numerical target was supplied in the card text.

## Reload, quality probe and outcome

The repeated trial completed with exit code 0. The final parameter digest equals
the saved/reloaded digest, and validation logits are bitwise equal, maximum
absolute error 0. The retained BF16 reference logits have shape `[1, 54, 129280]`.
Heldout loss changed from 4.5601024628 to 4.5665259361 (slightly worse). This single
54-token probe is the quality assessment available within this pilot; it does
not establish generalization or useful fine-tuning. Neither a quality improvement
nor a throughput target is claimed.

Across both timed updates, 126 actual tokens / 865.244816 seconds =
0.14562352 tokens/s. Preparation, validation and reload are outside that figure.
The repeated process peak RSS through reload was 7,025,086,464 bytes; the separate
cache conversion peaked at 17,249,882,112 bytes. GPU peaks reported in the table
are torch allocator counters, not a measurement of every driver allocation.
The runtime counted 66,267 expert fetches and 1,641,606,414,336 logical expert
bytes before reload, with one reusable expert slot. These counters do not
represent independently measured physical-host NVMe traffic.

The [machine-readable verdict](evidence/b6-20261028/real-giant/verdict.json) checks
the giant geometry/source manifest, ordered updates, gradients, digest chain,
actual token timings, memory bounds, finite heldout losses, exact reload and
completion. It explicitly leaves `ram_32gb_hardware_validated: false`.
The available NVMe filesystem was 1400 GiB, rather than the proposed roughly
2 TB, with sufficient measured free bytes for this source/cache combination.

All four B6 instances are independently verified absent after collection; no
persistent volume was created. Vast's post-deletion ledger query totals
**$3.707** including the three earlier smoke attempts ($0.090) and this real
lease ($3.617), with compute/storage/network rows retained. This is the ledger
as of the receipt timestamp, not a promise about later billing adjustments.
It is below the user's $5 total limit. No paid resource is left running.
