# Правило решения: ordinary и complete streaming на Kanana, этап 1

Это правило коммитится до первого запуска этапа 1 (тикет 06, `benchmarks/METHOD.md`: "Commit the rule before the first arm, and do not edit it after"). После коммита ни один порог, исход или обязательная проверка не меняется. Время коммита должно предшествовать `box_stamp_before.unix_s` первой записи `ArmWatch`.

Источники: план `benchmarks/streaming-ordinary-vs-complete-l2l-plan-20261114.md`, протокол `benchmarks/streaming-ordinary-vs-complete-l2l-protocol-20261114.md`, метод `benchmarks/METHOD.md`. Код: `benchmarks/harness/oc_arm_run.py`, `benchmarks/harness/oc_stage1_drive.py` (константа `REQUIRED` равна списку обязательных проверок ниже).

## Охват и решения пользователя

- Руки: `ga_ordinary`, `ga_complete`, `l2l_ordinary`, `l2l_complete`, `ga_floor` (только для допуска). Сравнения C1 (`ga_ordinary` против `ga_complete`) и C2 (`l2l_ordinary` против `l2l_complete`). Контрольной руки с кэшами экспертов нет (решение 2026-11-14).
- k: 1, 2, 4 полным методом (ABBA, пилот 5 блоков). k = 8 одним запуском каждой руки без ABBA, характеристика, вердикта нет (вариант A, 2026-11-14).
- Потолок этапа 1: 5 USD и около 10 часов. `expert_host_cache_bytes` равно 8 GiB у complete.
- Модель Kanana-2-30B-A3B-base-2601, ревизия `0d31365acf656e5f9a593cacc4913e9c0d36cb1c`. Рецепт: NF4 с двойным квантованием, BF16, FP32 LoRA на `q_proj`, `kv_b_proj`, `o_proj` (ранг 4, альфа 8), 512 токенов, batch 1, 8 обновлений (2 прогревочных).

## Правило решения

### Строки валидности

Эта таблица копируется в файл правила как есть. Каждая обязательная проверка идёт в `required` каждого `ArmWatch`.

| Строка валидности | Проверка | Обязательная | Если не выполнена |
|---|---|---|---|
| `suspend` ok на каждом запуске, который читает вердикт | `suspend` | да | нет вердикта |
| `power` ok на каждом запуске, который читает вердикт | `power` | да | нет вердикта |
| `foreign_reads` ok на каждом запуске, который читает вердикт | `foreign_reads` | да | нет вердикта |
| захват точности рук сравнения прошёл (раздел "Точность раньше тайминга") | точность | да | нет вердикта, руку не меряют |
| запись `gpu_clock` читается в каждом запуске, активные `sw_power_cap` и `sw_thermal_slowdown` выписываются в отчёт | запись, не проверка | нет | порога нет, вердикт не меняется |
| чтений эксперта на попадание у `l2l_complete` равно 3 | счётчик | да | остановка этапа |

Исход void не используется: блок с void-запуском заменяется новым (`blocks_to_add` делает это сам). Unknown у обязательной проверки даёт NO VERDICT для сравнения на этом k. Исключений для unknown нет, оправдание исключения должно быть закоммичено до измерения.

Строка с записью `gpu_clock` стоит здесь потому, что `METHOD.md` приводит случай 2026-10-09: все три проверки были ok при GPU, зажатом на 210 МГц.

### Строки вердикта

Число запуска: медиана шести измеряемых шагов оптимизатора (после двух прогревочных). Разность блока: среднее двух запусков A минус среднее двух запусков B. Тест: двусторонний t-тест на разностях блоков, alpha 0.05. Это тот же тест, на котором `METHOD.md` построил формулу числа блоков.

Эффект для сравнения на данном k: относительное сокращение шага `(mean A - mean B) / mean A`.

| Исход | Условие |
|---|---|
| WIN | t-тест значим и сокращение не меньше 10% |
| SMALL | t-тест значим и сокращение от 0 до 10%, в выигрыш не засчитывается |
| NO DIFFERENCE | t-тест не значим. Это не доказывает отсутствие эффекта меньше порога, формула числа блоков рассчитана на обнаружение 10% |
| LOSS | t-тест значим и complete медленнее |
| NO VERDICT | не выполнена обязательная строка валидности или не набраны блоки |

Порог эффекта 10% взят из `METHOD.md` и решений пользователя. Порог 2% из PR #5 не используется: при нём потребовалось бы примерно в 25 раз больше блоков.

Только отчёт, в вердикт не входит: время установки и всего запуска из 8 обновлений, VRAM allocated и reserved, RSS, чтения эксперта на попадание и на окно, ток/с (`512 * k / шаг`). Справочная проверка "кривая в пределах ±30% от расчёта плана P3" записывается как информационная и успехом не считается.

### Точность раньше тайминга

До блоков ABBA каждая рука проходит захват: два обновления AdamW, k микробатчей на обновление, одни и те же строки (случайные токены, 512, фиксированное зерно, вид данных `synthetic`). Захват делается при k = 2 (масштаб PR #5) и при k = 8 (наибольшее k этапа). Сохраняются градиенты LoRA, потери, параметры после обновления и состояние AdamW.

| Пара | Критерий |
|---|---|
| tiny, CPU | побитово, выполнено тикетом 03 (32 клетки, включая состояние AdamW) |
| Kanana: `ga_complete` против `ga_ordinary` | допуск A3: в bf16 относительная L2-ошибка градиентов LoRA и потери на каждом шаге не больше 1.5 раза шума. Побитовое равенство сообщается отдельно, как в PR #5 |
| Kanana: `l2l_complete` против `l2l_ordinary` | тот же допуск A3 |
| Kanana: `l2l_ordinary` против `ga_ordinary` | тот же допуск A3 |

Шум в допуске A3 это расстояние между GA на SDPA-бэкенде MATH и GA на EFFICIENT_ATTENTION в том же запуске (`FLOOR_FACTOR = 1.5`, `l2l_mistral_stand.py`). Для Kanana нужен ещё один захват, `ga_floor`. Допуск не ослабляется никакой опцией.

Если рука не прошла допуск, она не получает блоков, а её сравнение получает NO VERDICT с причиной "точность". Принятие предела по расхождению потерь L2L и GA от 2026-10-28 относится к тикету 04 этапа A5 на Mistral-7B. На Kanana оно не действует: промах пары с L2L останавливает этап, и пользователь решает отдельно.

### Число блоков

1. Пилот: 5 блоков на каждое сравнение и каждое k. Пилот входит в итоговый тест.
2. `blocks_to_add` считает N по формуле `ceil(7.85 * (sigma / delta)^2)`, где delta равна 10% среднего A, и один раз пересчитывает N по всем блокам. Больше N не пересчитывается.
3. Sigma берётся из пилота на этом хосте. Числа другой карты, другого хоста или запуска от батареи не используются.
4. Блок с void-запуском не считается, его записи сохраняются, добавляется замена.
