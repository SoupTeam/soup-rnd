### Actual FSDP implementation

Soup's presets contain older FSDP options and do not set a version. The installed
Transformers 5.17.0 owning source, `TrainingArguments._build_fsdp_plugin_args`,
defaults `fsdp_config['version']` to **2**. Names and old options alone cannot
establish FSDP1 or FSDP2. The harness records `fsdp_plugin.fsdp_version` at runtime
and checks actual FSDP modules. Unknown implementations fail admission.

For FSDP2, both physical parameter accounting (`to_local`) and reconstructed
adapter/gradient snapshots (`full_tensor`) use DTensor APIs. For FSDP1, accounting
uses the actual original-parameter shard views after wrapping; full snapshots use
`summon_full_params(writeback=False, with_grads=...)`. No division of a global
count is substituted for a measurement. Counts may be uneven; all local views
must sum to the pre-wrap logical count, every rank must hold less than the total,
and every rank must have real FSDP units. The single-GPU control must hold the
full count and have no FSDP units. Only GPU execution can validate these readings.

The data deliberately tests plumbing; it cannot establish quality, generalization
or a useful loss decrease. Smaller models can scale negatively under FSDP; an
honest speedup below one is a valid measurement, not grounds to change the rule.

### Assertions and numeric rules

- All returned microstep losses are checked finite after timing. Correctness and
  final inspection steps reconstruct every trainable gradient, require finite
  values and at least one nonzero gradient, and reject frozen-base gradients.
- Initial adapter keys/values must survive wrapping. After real optimizer steps,
  at least one adapter tensor must change. A first-step zero change in LoRA A is
  allowed. Rank-local frozen-base shard hashes before/after training must match.
- Reduced reconstructed gradients and reconstructed trained adapters must agree
  across ranks. Local sharded tensors themselves are **not** expected to be equal.
  The campaign also compares first-step gradients/adapter against the one-GPU
  reference on the same global data window (`atol=1e-5`, `rtol=0.02`): a narrow
  BF16/reduction-order plumbing check, not full-trajectory parity.
- Every microbatch shape and actual microbatch count per optimizer step are
  checked. First two global accumulation windows must contain exactly 8 distinct
  sample hashes, without cross-rank duplicates; their multisets must match the
  one-GPU control. The entire prepared token/label dataset and base-file hashes
  are verified before training, outside timing.
- Final root and checkpoint adapters reload in separate Python processes over
  the same local immutable base. Complete canonical adapter keys **and exact
  tensor values** must match the pre-save snapshot. Fixed 1×64-token eval logits
  must be finite and close: BF16 `atol=1/64`, `rtol=1/128`, allowing two absolute
  BF16 ULPs near one plus one relative ULP for kernel/reduction-order variation.
  FP32 offline fixture uses `atol=rtol=1e-5`. Exact adapter equality separately
  prevents a permissive logit tolerance hiding missing/dead adapters.
- Checkpoint files and byte counts are retained. This is **adapter reload**,
  not optimizer/scheduler/RNG restoration. Resume is unmeasured.

## Measurement and evidence

Input tokens/s = sum of actual nonpadding input tokens over **all ranks** divided
by the slowest rank's sum of CUDA-synchronized measured optimizer-step durations.
For this fixed no-padding shape each sequence contributes 512 input tokens and
511 causal loss targets. Do not substitute one rank's throughput or target tokens
into that numerator. Mean step seconds uses the same denominator / 20.

Timing runs from `on_step_begin` to `on_step_end`, including input preparation,
forward/backward, synchronization, optimizer and scheduler. Trainer's CPU batch
fetch before that callback, model/data loading, heavy correctness probes, warmup,
checkpointing, final eval and reload are excluded. This measures the training
compute loop, not an end-to-end job or input-pipeline throughput. Logging/progress
may appear outside the window; no torch.compile is enabled.

CUDA peak allocated/reserved statistics reset before the measured phase and are
recorded on each rank before later evaluation/saves. The warm allocator cache is
retained. Correctness gathers can affect cached reserved memory, particularly
with FSDP1; these peaks are not a claim about minimal possible VRAM. A background
50 ms sampler records per-rank process RSS and system-wide used host RAM during
the same phase. These are sampled peaks (short spikes can be missed); summed RSS
is not unique physical RAM because shared pages may be counted more than once.

Every arm keeps resolved SoupConfig, benchmark controls, raw command/exit/log,
rank readings, initial-step adapter/gradients, final reload reference, checkpoint
files, commit and dirty status, harness hashes, Python/package versions, pip
freeze, CUDA/NCCL info, GPU inventory and topology. The campaign refuses a dirty
checkout, nonidentical GPU models, active foreign compute processes, failed or
incomplete ranks/reloads, data/config/host/version mismatches and first-step
comparison failures. Raw failing attempts remain diagnostic and cannot enter the
summary. A failed revalidation invalidates any earlier summary.

Speedup(2) = median throughput(2) / median throughput(1).
Efficiency(2) = speedup(2) / 2. Report all repeats and raw rank times alongside
the medians; with three pairs no narrow confidence interval is claimed.

## Linux commands and stop criteria

Use a dedicated two-GPU Linux server with Python 3.10–3.12, driver supporting
CUDA 13.0, at least 32 GB host RAM and 60 GB disk allocation. Verify more than
15 GB disk remains before starting arms. Clone/check out the PR commit cleanly.
From the repository root:

```bash
bash benchmarks/h3-fsdp-linux.sh
```

The script creates an isolated venv, installs CUDA torch and the pinned pilot
stack, runs `pip check`, prepares the immutable model/data, then calls:

```bash
export PYTHONPATH="$PWD/src"
python benchmarks/harness/h3_fsdp_campaign.py \
  --prepared benchmarks/evidence/h3-fsdp-20261026/prepared \
  --output benchmarks/evidence/h3-fsdp-20261026/live/campaign \
  --repeats 3 --timeout-seconds 900 --campaign-seconds 5400
```

Individual one-GPU/two-GPU training commands and each separate reload are emitted
to `*.command.json`. The two-GPU entry uses
`python -m torch.distributed.run --standalone --nnodes=1 --nproc-per-node=2 ... train`.
The one-GPU entry exposes only GPU 0 to prevent accidental DataParallel.

Stop on the first error, nonfinite state, OOM, failed update/base/shard/data/reload
assertion, missing rank, dependency conflict, insufficient disk or NCCL hang.
There are no automatic retries or runtime dependency upgrades. Each command has
a 15-minute limit; the campaign has a 90-minute wall limit. On timeout its own
torchrun process group is terminated, including workers. These limits do not
destroy a rented server or cap billing: the operator must separately enforce
the approved rental deadline, collect results, and destroy the instance/disk.
Allow at most 30 minutes setup plus 90 minutes campaign in the proposed pilot.

Recompute a report only from complete retained arms:

```bash
python benchmarks/harness/h3_fsdp_campaign.py --summarize-only \
  --prepared benchmarks/evidence/h3-fsdp-20261026/prepared \
  --output benchmarks/evidence/h3-fsdp-20261026/live/campaign
```

The live/prepared/venv directories are ignored; copy them off the server before
destruction. Retain the immutable base revision/manifests and dataset, and commit
the raw logs/configs/readings/summary for a hardware follow-up. Adapter/tensor
artifacts can be archived with their SHA256 manifest if kept outside Git.
